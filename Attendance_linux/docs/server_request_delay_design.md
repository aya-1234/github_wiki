# サーバー操作間隔制御 実装計画

## 1. 要件整理

| 項目 | 内容 |
|---|---|
| 実現したい内容 | Salesforce勤怠管理システムへの連続操作を抑え、サーバー負荷を軽減する |
| 現状 | cronは平日1日1回だが、1回の処理内にサーバー通信を伴う画面遷移・保存・申請操作の間隔制御がない |
| 制約条件 | DOM監視やローカル文字入力には待機を加えず、既存のタイムアウト設定とは分離する |
| 成功条件 | サーバー通信を伴う操作が既定で最低5秒間隔になり、環境変数で0～300秒に変更でき、既存機能が退行しない |

## 2. 調査結果

- `attendance_login/login.py` の0.5秒待機は画面状態を確認するDOMポーリング用であり、サーバー操作の流量制御ではない。
- 初期ページ遷移、SSO、勤務時間保存、日別情報保存、工数入力、日次申請の各操作は、同一実行内で連続する可能性がある。
- `Config` は環境変数の整数値を範囲検証する既存機構を持つため、同じ方式で操作間隔を追加できる。
- 1回の実行全体で間隔を共有しないと、機能間の境界で連続アクセスが起こり得る。

## 3. 実装計画

1. **変更対象**
   - `attendance_login/config.py`
   - `attendance_login/pacing.py`（新規）
   - `attendance_login/main.py`
   - `attendance_login/login.py`
   - `attendance_login/work_hours.py`
   - `attendance_login/workload.py`
   - `attendance_login/daily_request.py`
   - `.env.example`、`README.md`、`docs/linux_setup_guide.md`
   - 関連テスト

2. **実装内容**
   - `SERVER_REQUEST_DELAY_SECONDS` を追加し、既定値5秒、許容範囲0～300秒とする。
   - 1回の実行で共有する `RequestPacer` を生成する。
   - 初回操作は直ちに実行し、2回目以降は前回のサーバー操作開始から設定秒数が経過するまで待機する。
   - ページ遷移および通信が発生し得るクリックの直前にレート制御を適用する。
   - DOMポーリング、要素検索、文字入力だけの操作には適用しない。

3. **影響範囲**
   - 通常実行、ログインのみ、dry-run、工数のみ、日次申請の所要時間が設定に応じて長くなる。
   - 待機時間はログイン・入力用タイムアウトとは独立しており、待機後に各操作を開始する。
   - サーバー操作を行わない判定・スキップ処理には待機を加えない。

4. **リスク**
   - 操作箇所の追加時にレート制御の適用を忘れる可能性があるため、共通オブジェクトと明示的な引数で可視化する。
   - 実行時間が増えるが、既定5秒かつ平日1回の運用では許容範囲と判断する。
   - ブラウザー内部のバックグラウンド通信を完全には制御できない。自動操作が開始する主要通信の間隔を制御対象とする。

5. **テスト方針**
   - 単体テスト: 初回即時、残り時間待機、十分な経過後は待機なし、0秒設定、設定値の境界・不正値。
   - 結合テスト: `main.run` が同じ `RequestPacer` をログインと各勤怠操作へ渡すことを確認する。
   - 非退行確認: 全pytestを実行する。
   - 手動確認: `--check-config` で設定読込を確認する。実サーバーへのアクセスは自動テストでは行わない。
