# 詳細設計書：API・処理・例外

[概要設計書](概要設計書.md)と[基本設計書](基本設計書.md)に基づく実装契約を定める。技術は Python / FastAPI、Git CLI、Poppler の `pdfinfo`・`pdftotext`、Python 標準ライブラリによる OOXML 読み取りとする。

## 1. モジュール構成

| モジュール | 責務 |
| --- | --- |
| `web` | 単一画面の配信、ファイル選択、Markdown 編集、プレビュー、結果表示。 |
| `api` | リクエストの検証、変換・公開サービスの呼び出し、エラー応答。 |
| `document` | PDF・Office からの文字抽出、Markdown 読込、警告生成。 |
| `page` | タイトル検証、本文正規化、ファイル名・URL の生成。 |
| `wiki_git` | 一時クローン、同名検査、Git commit/push、競合の分類。 |

依存方向は `web → api → document/page/wiki_git` とする。`document` は GitHub と通信しない。

## 2. API

`POST /api/convert` はファイルを変換するだけで、公開しない。`POST /api/preview` は編集本文を安全な HTML に描画する。`POST /api/publish` は画面で確認済みのタイトルと本文を受け取り、GitHub Wiki に公開する。両 API の入力値はサーバーで再検証する。

### 2.1 `POST /api/convert`

`multipart/form-data` の `file` に単一ファイルを指定する。最大 20 MiB。成功は HTTP 200。`warnings` は変換時の警告と相対参照の警告、`sourceWarnings` は PDF 抽出など変換固有の警告を返す。

```json
{
  "title": "操作手順",
  "markdown": "## PDF 1ページ目\n\n...\n",
  "warnings": ["相対リンク: ./guide.md — Wiki での参照先を確認してください"],
  "sourceWarnings": []
}
```

失敗は `400 INVALID_FILE` / `413 FILE_TOO_LARGE` / `422 UNSUPPORTED_FORMAT`、`PDF_NO_TEXT`、`PDF_ENCRYPTED`、`PDF_TOO_MANY_PAGES`、`INVALID_ENCODING`、`EMPTY_DOCUMENT` のいずれか。Office の破損・形式不一致は `422 INVALID_FILE`。Poppler の実行失敗は API で利用者向けの `INVALID_FILE` などに変換する。

### 2.2 `POST /api/preview`

`application/json` の `markdown` を受け取り、HTML と相対参照の警告を `{"html":"...","warnings":["..."]}` で返す。Markdown 内の HTML は無効化し、危険な URL スキームはリンク化しない。画面は最後のプレビュー応答だけを反映し、変換固有の警告は保持する。

### 2.3 `POST /api/publish`

`application/json`。`repository`、`title`、`markdown` は必須。公開要求にファイル原本は送らない。本文は UTF-8 で最大 2 MiB。

```json
{
  "repository": "owner/repository",
  "title": "操作手順",
  "markdown": "# 操作手順\n\n本文\n"
}
```

成功は HTTP 201。`pageUrl`、`wikiUrl`、`commitSha` を返す。たとえば `{"pageUrl":"https://github.com/owner/repository/wiki/%E6%93%8D%E4%BD%9C%E6%89%8B%E9%A0%86","wikiUrl":"https://github.com/owner/repository/wiki","commitSha":"..."}`。URL のパス要素はサーバーでパーセントエンコードして返す。

| HTTP | エラーコード | 原因・UI の案内 |
| --- | --- | --- |
| 400 | `INVALID_REPOSITORY` / `INVALID_TITLE` / `EMPTY_DOCUMENT` | 入力を修正する。 |
| 401 | `GIT_AUTH_FAILED` | Git の認証設定を確認する。 |
| 403 | `WIKI_WRITE_DENIED` | Wiki 編集権限を確認する。 |
| 404 | `WIKI_UNAVAILABLE` | Wiki の有効化と初期ページを確認する。 |
| 409 | `PAGE_EXISTS` | 別のページ名を指定する。 |
| 409 | `REMOTE_CHANGED` | 最新の Wiki を確認してから再試行する。 |
| 413 | `CONTENT_TOO_LARGE` | 本文を短くする。 |
| 502 | `GIT_REMOTE_ERROR` | 接続状態を確認する。再送前に Wiki も確認する。 |
| 504 | `GIT_TIMEOUT` | 時間切れ。Wiki への反映の有無を確認する。 |

すべての失敗応答は `{"code":"...","message":"..."}`。内部の Git stderr、ローカルパス、認証情報は API 応答に含めない。

## 3. ファイル変換処理

1. ストリームを読みながら 20 MiB を超えた時点で停止する。ファイル名と拡張子を検査する。
2. `.pdf` はヘッダーとパーサーで実体を確認し、暗号化とページ数を検査する。1 ページずつ文字を抽出して空白を整える。抽出テキストが全文で空なら `PDF_NO_TEXT`。ページごとに `## PDF Nページ目` を挿入する。抽出文字が極端に少ない場合は警告を出すが、空でなければ編集を許す。
3. `.md` は UTF-8 または UTF-8 BOM として厳密に復号する。CRLF/CR を LF に統一する。NUL は拒否する。
4. `.docx` / `.xlsx` / `.pptx` は OOXML ZIP の必須 XML を確認し、展開後 50 MiB・2000 項目を上限に解析する。Word は本文の段落・見出し・表、Excel はシート順のセル値、PowerPoint はプレゼンテーション定義順のスライド文字列を Markdown にする。テキストは Markdown 特殊文字をエスケープする。画像・図形・書式の欠落を警告する。
5. ファイル名の拡張子を取り除き、NFC 正規化したページ名候補を返す。候補が不正でも変換結果は返し、画面で修正を求める。
6. Markdown として認識される相対リンク・画像参照を検出し、参照先を示して警告する。インライン・参照形式の両方を扱う。警告は本文を勝手に修正しない。

PDF の文字抽出は段組み・表・装飾を忠実に再現できない。画面で本文確認と修正を必須にする。

## 4. ページ名・本文の検証

`repository` は `owner/repository` の 2 要素のみを許す。各要素は GitHub.com のリポジトリ指定として安全な英数字、`-`、`_`、`.` のみに限定し、先頭・末尾の `.` と `..` を拒否する。URL は固定の `https://github.com/` と、検証済み要素から組み立てる。任意 URL は受け付けない。

`title` は NFC 正規化後、1〜100 文字、前後空白なし、制御文字と `\\ / : * ? \" < > |` を含まないこと、末尾が `.` でないこと、予約名でないことを検査する。パスの子要素を生成せず、保存ファイルは一時クローン直下の `<title>.md` に限定する。`markdown` は LF 正規化後に空白だけでないことと UTF-8 最大 2 MiB を検査する。

## 5. Wiki 公開処理

Git はコマンド配列で起動し、`shell=True` を使わない。公開処理全体を同一アプリ内で 1 件ずつ実行する。各要求には独立した一時ディレクトリを使う。

1. `repository` を検証し、リモートを `https://github.com/<owner>/<repo>.wiki.git` として組み立てる。Git 認証ヘルパーの設定を利用し、対話プロンプトは無効にする。
2. 一時ディレクトリへ Wiki を `git clone` する。初期ページ未作成、権限不足、通信障害を可能な範囲で分類する。曖昧なエラーは `GIT_REMOTE_ERROR` とする。
3. チェックアウトされたブランチがリモートのデフォルトブランチであることを確認する。開始時 HEAD を `baseSha` として記録する。
4. クローン直下の既存ファイル名を NFC・casefold で比較し、同名なら `PAGE_EXISTS`。特別ページと、拡張子違いの同名ページも衝突と扱う。
5. `<title>.md` を UTF-8 で書き、対象の 1 ファイルだけ `git add -- <filename>` する。`git commit -m "Add wiki page: <title>"` を実行し、`commitSha` を得る。Git author 名とメールはアプリ用の固定値を設定可能にする。
6. `git push origin HEAD:<defaultBranch>` を実行する。強制プッシュしない。非 fast-forward は `REMOTE_CHANGED`。競合時は新しいクローンを作って、同名ファイルの有無を再確認する形での手動再試行を案内する。
7. 成功後にページ URL を作って返す。終了時は成功・失敗にかかわらず一時ディレクトリを消す。

同一アプリ内の二重クリックは UI とロックで抑える。複数プロセスや GitHub 上での同時編集は Git の非 fast-forward を最終的な競合検出とする。プッシュがタイムアウトした場合、公開されたかは断定しない。

GitHub Wiki の Git クローン・デフォルトブランチでの公開・ファイル名ルールは [GitHub Docs: Adding or editing wiki pages](https://docs.github.com/en/communities/documenting-your-project-with-wikis/adding-or-editing-wiki-pages) に基づく。

## 6. 時間・一時領域・ログ

- 変換は 30 秒、Git 公開は 120 秒を上限とする。超過した子プロセスは終了し、後処理を行う。
- 一時クローンとアップロード内容は OS の一時領域に置く。API がディスクに一時保存した場合も `finally` で削除する。
- ログは要求 ID、処理段階、所要時間、エラーコードを記録する。原本、本文、秘密情報、Git の生 stderr は記録しない。
- localhost サーバーは `127.0.0.1` に限定し、`Host` と `Origin` を検査する。公開 API は JSON のみを受け付け、外部サイトからのブラウザ経由の送信を拒否する。
- HTML プレビューは Markdown を変換した後にサニタイズし、スクリプト・イベント属性・危険な URL スキームを除去する。編集欄への表示には HTML として挿入しない。

## 7. 検証計画

| 種別 | 確認すること |
| --- | --- |
| 単体 | UTF-8/BOM、PDF のページ順、空文書・画像 PDF・暗号化 PDF、タイトル検査、相対リンク警告。 |
| API | `convert` と `publish` の正常応答、サイズ超過、入力不正、サニタイズ済みプレビュー。 |
| Git 統合 | ローカルの bare Git リポジトリを Wiki と見立てて新規追加、同名拒否、非 fast-forward を再現する。 |
| 手動 | 権限のあるテスト Wiki で PDF と Markdown を各 1 件公開し、表示・URL・コミットを確認する。 |

実 GitHub への手動公開は、テスト用 Wiki と認証設定が利用可能になった時点で行う。

## 8. PR 経由の Wiki 登録

`scripts.stage_wiki_page` は既存の `convert` を使って文書を Markdown 化し、タイトル・本文を検証して `wiki-pages/<title>.md` に新規作成する。同名ファイルは上書きしない。

画面は変換・編集後のタイトルと本文を `POST /api/stage` に送信する。API は `wiki-pages/<title>.md` を排他的に新規作成して HTTP 201 と相対パスを返し、同名は HTTP 409 とする。直接公開の `POST /api/publish` は環境変数 `ALLOW_DIRECT_WIKI_PUBLISH=1` を明示した場合だけ有効にする。

`.github/workflows/publish-wiki.yml` は PR 時に `scripts.wiki_pr validate` を実行する。PR のマージベースから追加された `wiki-pages/*.md` だけを受け付け、既存ページの変更・削除と階層化を拒否する。この段階では秘密情報を利用しない。

`main` への push 時は、その push で追加されたページを再検証してから `wiki_app.publish` を呼ぶ。Git 認証は Actions secret `WIKI_PUSH_TOKEN` を `GIT_ASKPASS` から渡し、リモート URL にトークンを埋め込まない。既存ページ・競合の拒否規則はローカル画面の公開処理と共通。初期 Wiki ページと Secret は利用者が GitHub 上で設定する。

PR 必須・承認必須・検証チェック必須は `main` のルールセットで強制する。設定前の直接 push でもワークフローは起動するため、ルールセットを本番運用の前提とする。
