# 概要設計書：文書から GitHub Wiki への登録

## 1. 目的

Markdown、PDF、Word、Excel、PowerPoint ファイルを選び、内容を確認してから指定した GitHub リポジトリの Wiki に新しいページを追加するローカル Web アプリを作る。手作業でのテキスト転記と Git 操作を減らし、誤った内容や既存ページの上書きを防ぐ。

本書は初版（MVP）の設計である。[基本設計書](基本設計書.md)に画面・機能・データを、[詳細設計書](詳細設計書.md)に処理・API・例外を定める。

**現行運用の追補:** 画面からの直接公開を PR 用 Markdown の保存に変更した。Wiki への反映は通常リポジトリの PR を審査・マージした後に GitHub Actions が行う。詳細は[基本設計書の PR 経路](基本設計書.md#pr-審査を通す公開経路)と[詳細設計書](詳細設計書.md#8-pr-経由の-wiki-登録)を参照する。以下は初版の直接公開設計を記録したもの。

## 2. 利用者と利用条件

- 利用者はローカル PC 上でアプリを起動する、Wiki への書き込み権限を持つ 1 人。
- 対象は GitHub.com の既存リポジトリ 1 件。Wiki 機能が有効で、初期ページが作成済みであることを前提とする。
- 認証には利用者の既存の Git HTTPS 認証設定（認証ヘルパー）を使う。アプリ自身は GitHub トークンを保存しない。
- ブラウザからローカルホスト上のアプリを操作する。サーバー公開・複数利用者・自動同期は初版の対象外。

## 3. 利用の流れ

1. 利用者が対象の `owner/repository` と、`.md` / `.pdf` / `.docx` / `.xlsx` / `.pptx` ファイルを指定する。
2. アプリがファイルを検査し、Markdown へ変換する。PDF はページ順、PowerPoint はスライド順に並べる。
3. 利用者がページ名と変換結果を確認し、必要なら本文を編集する。
4. 利用者が「Wiki に追加」を実行する。
5. アプリが Wiki 用 Git リポジトリの最新状態を取得し、同名ページがないことを確認して、1 ページだけコミット・プッシュする。
6. 成功時は公開ページの URL とコミット ID を表示する。失敗時は原因と再試行方法を表示する。

```mermaid
flowchart LR
    A[Markdown / PDF / Office] --> B[形式・サイズ検査]
    B --> C[テキスト抽出・Markdown 化]
    C --> D[プレビューと編集]
    D --> E[同名ページ確認]
    E --> F[Wiki Git リポジトリへコミット・プッシュ]
    F --> G[ページ URL を表示]
```

## 4. 初版の対象範囲

| 項目 | 方針 |
| --- | --- |
| 入力 | 単一の `.md` / `.pdf` / `.docx` / `.xlsx` / `.pptx`。1 ファイルから 1 ページを生成する。 |
| PDF | 埋め込みテキストを抽出する。各 PDF ページの境界を見出しとして残す。スキャン画像だけの PDF は登録せず説明を出す。 |
| Markdown | UTF-8 テキストとして読み込み、本文を初期値にする。 |
| Office | Word の段落・見出し・表、Excel のシートとセル値、PowerPoint のスライド内テキストを抽出する。画像や書式は移送しない。 |
| 確認 | ページ名、Markdown 本文、簡易プレビュー、変換時の警告を表示する。 |
| 公開 | 新規ページ追加のみ。既存ページ、`Home`、`_Sidebar`、`_Footer` は上書きしない。 |
| 競合 | 同名ページと Git の更新競合を検出し、勝手に上書きしない。 |

## 5. 対象外と今後の拡張候補

- OCR、画像や添付ファイルの抽出・アップロード、PDF のレイアウト完全再現。
- 複数ファイルの一括登録、既存ページの更新・削除、定期同期、AI による要約・分類。
- GitHub Enterprise Server、複数利用者向け認証、サーバーへの常設公開。

これらを追加する場合も「変換結果を確認してから公開する」「既存ページを暗黙に変更しない」を維持する。

## 6. 構成と責務

| 要素 | 責務 |
| --- | --- |
| ブラウザ画面 | ファイル選択、ページ名・本文編集、警告・結果表示。 |
| ローカル API | 入力検査、PDF 抽出、Markdown プレビュー、公開要求の制御。 |
| Git 作業領域 | 対象 Wiki の最新状態を一時的に取得し、1 ファイルをコミットする。 |
| GitHub Wiki | 公開先。通常のコードリポジトリとは別の `.wiki.git` リポジトリ。 |

実装技術は Python / FastAPI、Poppler の `pdfinfo`・`pdftotext`、Git CLI とする。Python パッケージの版は `uv.lock` で固定する。GitHub Wiki は Git リポジトリとしてローカル編集とプッシュが可能で、デフォルトブランチへプッシュした変更が公開される。ページ名はファイル名で決まる。根拠：[GitHub Docs: Adding or editing wiki pages](https://docs.github.com/en/communities/documenting-your-project-with-wikis/adding-or-editing-wiki-pages)。

## 7. 品質・安全性

- 公開前に必ずプレビューを挟み、公開操作を明示的に行う。
- アップロード上限は 20 MiB、PDF は 100 ページまでとする。超過時は処理前に拒否する。
- ファイル内容は処理用の一時領域だけに置き、処理後に削除する。ログに本文や認証情報を出さない。
- Git の操作先を GitHub.com の `owner/repository.wiki.git` に限定し、利用者入力をシェル文字列へ連結しない。
- 既存ページの同名判定、公開競合の検出、プッシュ失敗時の明確な通知を行う。
- GitHub Wiki 自体にはファイル総数 5,000 件のソフト制限があるため、大規模登録には別方式を検討する。根拠：[GitHub Docs: About wikis](https://docs.github.com/en/communities/documenting-your-project-with-wikis/about-wikis)。

## 8. 完了条件

1. テキスト入り PDF と UTF-8 Markdown から、プレビュー可能な 1 ページを生成できる。
2. 利用者が編集したページ名・本文が、新規 GitHub Wiki ページとして公開される。
3. 同名ページ、空文書、画像のみの PDF、サイズ超過、認証失敗、プッシュ競合で意図しない公開や上書きをしない。
4. 成功時にページ URL を、失敗時に復旧に必要な理由を表示する。

## 9. 設計上の前提・未決事項

初版はローカル単独利用、GitHub.com、既存 Wiki、単一ファイル入力を前提とする。公開運用、OCR、添付ファイル、既存ページの更新が必要になった場合は別要件として設計を拡張する。
